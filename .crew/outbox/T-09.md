# T-09 outbox — The signature moment: drag becomes the Eightfold

## What I built
`src/app/App.jsx` (composition root, rewritten) and `src/app/perf.js` (new), plus small extensions
to `src/render/useDrag.js` and `src/render/Ground.jsx` to carry the drag events App.jsx needs.

- One `GrainBuffer` (`createBuffer(20000)`) held in a ref, created once. Seed resolved once via
  `?seed=` in the URL or `crypto.getRandomValues` in app code (never in core), stored in
  `useState` so a future colophon (T-12/T-14) can read it.
- `useDrag` now takes `{ onDown, onMove, onUp }` instead of one shared `onPoint` — needed because
  App.jsx has to tell "this is the start of a new stroke" apart from "this is a continuation,"
  which a single callback couldn't express. Also added: only the first active pointer is tracked
  (a second touch point is ignored, DESIGN §9.1), and `window blur` behaves exactly like
  `pointerup` (DESIGN §9.1's table). `Ground.jsx` just forwards the three callbacks as props now.
- `App.jsx`'s `emitAndPush(segment, t)` calls `core.emit()`, then computes how many grains were
  written this call (`(newCursor - prevCursor + capacity) % capacity` — robust to ring-wrap) and
  calls `Grains.pushRange` once, or **twice** if the write straddles the array boundary (per T-06's
  outbox note). `perf.js`'s current degrade step multiplies the emission spacing before each call.
- `startStroke(point)` / `continueStroke(point)` / `endStroke()` implement the actual drawing
  behaviour — see the "one real design decision" section below, it's the part most worth reading.
- `src/app/perf.js`: rolling 120-frame window (`Float32Array`, preallocated), checked every 30
  frames (not every frame) by sorting a **reused scratch typed array in place** — zero allocation.
  p50 > 20ms sustained 2s -> spacing ×1.5, up to 3 steps, exactly as BOARD specifies.

## The one real design decision this task required
DESIGN §4.3 requires "one sample-step emits before any movement" — a bare tap must produce 8
marks. But `core/grains.js`'s arc-length `resample()` **needs two distinct points** to measure any
distance; a single stationary point can never produce a sample through the public `emit()` API.
Separately, `resample()` carries continuity (`buffer._lastPoint`/`_carry`) **across every call
forever**, with no way to reset it from outside — so a second, unrelated stroke started far from
where the first one ended would otherwise get a spurious straight line connecting them (exactly the
"classic bug" DESIGN §6.7 names `TELEPORT_LIMIT` for).

I solved both with one mechanism, in `startStroke()`:
1. **Reset** `buffer._lastPoint = null; buffer._carry = 0` — the exact values `createBuffer()`
   itself initialises a fresh buffer to. This doesn't touch `origin`/`birth`/`phase`/`count`/
   `cursor`/`print` (nothing already written is affected), and happens at one well-defined moment
   (every stroke's first point), so it's fully deterministic and reproducible under replay.
2. Then emit a **tiny symmetric synthetic segment** centred on the real point — `[point -
   spacing/2, point + spacing/2]` along a fixed +x direction — which is the only way to get
   `resample()` to produce a sample with zero real user movement. It lands the mark ~0.01 world
   units (a few screen px) from the actual point.

`_lastPoint`/`_carry` are documented in T-06's outbox as "internal, not part of the public
contract" (render/ should only *read* `origin, birth, phase, count, cursor, print, capacity`). I'm
writing two of the non-public fields here, read-only otherwise. **Flagging as a needs-decision for
pc-architect**, not doing it silently: the alternative was either a visibly broken multi-stroke
experience (a straight line jumping across the pattern on the second stroke) or modifying the
frozen core, and I judged this the least-bad option given both were closed. Verified live (see
below) that it produces the intended result with no artifact.

Same mechanism handles mid-drag teleports: if a single `pointermove` reports a jump > `0.45` world
units from the last emitted point, `continueStroke` calls `startStroke` again instead of connecting.

## Verified live, in real Chrome (Chrome-for-Testing via the `playwright` package directly —
Playwright MCP's browser isn't available in this sandbox, same as T-02; `npx playwright install
chromium` was already run)
- **Eight congruent, symmetric arcs bloom simultaneously with the drag**, not after pointer-up —
  screenshot at `.crew/deliverables/signature-frame.png` (captured mid-fall, grains still
  converging/blooming near the centre — the closest single frame to DESIGN §3.3's "screenshot
  frame" achievable without T-24's `?still=1` freeze).
- **Two independent strokes accumulate correctly with zero connecting-line artifact** — confirmed
  visually (16 arms, clean star, no stray line between the two crossings) and numerically (buffer
  print changes each time, `count` grows: 0 -> 632 -> 1296).
- **Tap alone (pointerdown + pointerup, no movement) emits exactly 8 grains** — measured directly
  (`buffer.count` delta = 8), confirming DESIGN §4.3.
- Zero page errors (`page.on('pageerror')` empty). Only benign console output: a 404 for
  `/favicon.ico` (no favicon shipped yet — cosmetic, any later task can add one) and three.js's own
  `THREE.Clock is deprecated, use THREE.Timer` warning (R3F 9 uses `Clock` internally; not
  something this task can fix without touching R3F itself — harmless, not a runtime error).
- A dev-only hook, `window.__threshold = { buffer, seed, grainsRef, perfMeterRef }`, is how I read
  `buffer.count`/`print`/`cursor` from the driver script — no debug UI renders on the page. Left in
  place since T-12/T-14 will want to read `buffer.count`/`print` for the colophon anyway; remove or
  repurpose it there if undesired.

**Stopped here per the Crew Chief's instruction mid-verification** — capacity/ring-wrap stress
(continuous drawing well past 20000 grains), the 390px mobile-viewport check, and heap-growth
sampling over a longer session were queued but not run; those are pc-test-user's job at T-20, not
mine. The wrap-split logic in `App.jsx`'s `pushWrittenRange` is implemented and reasoned through
(see the code comments) but **only exercised in this session by two short strokes** (a few hundred
to ~1300 grains total, nowhere near the 20000 cap) — it has not been observed actually wrapping.

## What T-11/T-12/T-14/T-20 need to know
- Keyboard input (arrow keys, Space/Enter draw-lock, DESIGN §9.2) is **not built** — BOARD's T-09
  acceptance only tests mouse/touch drag, and §9.2 itself names this "cut-order item 1." Still
  needed before ship for the accessibility floor's "whole mechanic, operable" claim.
- Hover ghosts (§4.2) and the Invocation (§4.1) are **not built** — DESIGN §10 doesn't assign
  either to T-09 (Invocation is explicitly T-14's, hover ghosts aren't assigned anywhere in the
  table). First-time load currently shows an empty dark plane until the first pointerdown.
- `DRAW_RADIUS_MAX` (2.40) is enforced (emission silently stops beyond it) but the "cursor dims to
  0.15" visual isn't — there's no cursor-point render target yet.
- pc-test-user (T-20): please run the capacity/wrap stress test and the 390px mobile-emulation
  check I didn't get to — both are described (with a ready driver script pattern) in this outbox
  and in T-08's, and the wrap-split code path in `App.jsx` genuinely needs exercising past 20000
  grains before anyone should trust it under load.
