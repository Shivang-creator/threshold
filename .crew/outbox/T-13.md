# T-13 outbox — Resilience: the fallback that is also the proof

## What I built
`src/frame/NoWebGL.jsx`, the WebGL probe (`src/app/detectWebGL.js`), an R3F error boundary
(`src/app/SceneErrorBoundary.jsx`), a `webglcontextlost` listener wired in `Scene.jsx`'s
`onCreated`, and the reduced-motion system (`src/app/useReducedMotion.js` + a new `uMotion` uniform
in `grain.vert.js` + `Grains.jsx`).

## The boundary proof — verified, not just claimed
`grep -n "^import" src/frame/NoWebGL.jsx` → exactly one line: `import { createBuffer, emit } from
"../core/index.js";`. No import of `react`, `three`, or anything in `render/`. Because of that
constraint, `NoWebGL.jsx` **cannot** import `TitlePlate`/`Colophon`/`grainConstants.js`/
`palette.js`/the shader's `hash11` — every one of those is duplicated as a literal inside
`NoWebGL.jsx` with a comment pointing at its real source of truth (same "known duplication,
disclosed" pattern the README already documents for `sim.js`/`grain.vert.js`, T-07). This is the
cost of the boundary being real rather than aspirational.

## Gap in DESIGN.md, filled with an invented default (flagged, not blocking)
DESIGN §8b calls for the fallback SVG to be built from "INVOCATION + 2 more authored strokes" but
gives control points only for the Invocation (§4.1). The other two strokes aren't specified
anywhere in DESIGN.md. I hand-picked two small arcs (`STROKE_B`, `STROKE_C` in `NoWebGL.jsx`, both
well inside `DRAW_RADIUS_MAX`) so the fallback shows a plausible multi-stroke kolam rather than
just the Invocation's own shape repeated. These coordinates are pc-frontend's own invention, not a
DESIGN.md value — flag for pc-designer if exact control points matter later.

## Detection order (DESIGN §8b), all three paths wired
1. `probeWebGL()` runs synchronously in `App`'s `useState` lazy initializer — a browser with no
   WebGL never mounts `<Scene>` at all. Verified: with `HTMLCanvasElement.prototype.getContext`
   monkey-patched to return `null` for any `webgl*` context type, the page renders the SVG kolam
   with the site frame intact, no WebGL canvas in the DOM, no `<text>` inside the `<svg>`, and the
   correct copy ("This browser could not open a 3D canvas...").
2. `SceneErrorBoundary` (a class component — error boundaries require one, there's no hook
   equivalent) wraps `<Scene>`; a render-time throw flips `sceneCrashed` and the same NoWebGL
   fallback renders. Not exercised live (nothing in this build currently throws on render) — this
   is a static-analysis-verified safety net, not a smoke-tested one.
3. `webglcontextlost` is attached to `gl.domElement` inside `Scene`'s `onCreated`, calls
   `event.preventDefault()` (per the WebGL spec, signalling the page will handle the loss itself)
   and flips `contextLost`, which swaps to `<NoWebGL contextLost={true}/>` — different copy ("The
   3D canvas was interrupted.") plus a kumkum-outlined RELOAD button. **Not exercised live** — I
   did not find a reliable way to force a real context-loss event from Playwright in the time
   available; this path is code-reviewed but not observed firing.

## Reduced motion — what actually happens to the print
`uMotion` is a pure **render** uniform on the grain shader (`grain.vert.js`): at `uMotion < 0.5` a
grain renders at its settled position immediately with a 200ms per-grain opacity fade-in (ordered
by `aBirth`, no new attribute needed), instead of running the fall/bounce curve. **Nothing about
this touches `core/grains.js`'s `emit()` or its buffer** — the buffer function never receives a
motion argument, exactly as DESIGN §8a's proof requires structurally, not just by convention.

I attempted to machine-verify this by loading two separate Playwright pages (one
`reducedMotion:'reduce'`, one default) concurrently and comparing `buffer.print` after the
Invocation — **first attempt showed different prints between the two**, which looked like a real
bug. Root-caused it to a test-methodology artifact, not a product bug: with two heavy WebGL pages
open in the same Chromium process concurrently, the non-focused page's `requestAnimationFrame` gets
throttled by the browser, so the Invocation (which paces its emission by real elapsed time across
frames) hadn't finished within the same wall-clock wait window in the throttled page. Re-ran with
pages opened **sequentially** (one fully closed before the next opens) at three different wait
times (3s/5s/8s) — prints matched exactly (`0672da95`) in every case, both reduced and normal.
**I'm confident in the reduced-motion-doesn't-touch-the-buffer claim from the code's construction**
(it's structurally impossible for `uMotion` to reach `emit()`), and reasonably confident from this
corrected test, but I did not get to re-run the single-session "toggle mid-session, compare
before/after" version of this check that DESIGN §8a and this board task's own acceptance criterion
#3 actually ask for, before the turn budget ran out. **pc-red-team: this is worth attacking
directly** — toggle the MOTION button mid-session on the live URL and diff the exact 8 hex
characters, which is a cleaner test than mine and matches the acceptance criterion literally.

Also wired: `prefers-reduced-motion` is read once at boot and stays **live** thereafter (a
`matchMedia` change listener), a manual MOTION-button choice is persisted to
`localStorage["threshold.motion"]` and wins over the OS setting once made, and the Breath/Noise
postprocessing were already gated on `reducedMotion` by T-11 — I only added the grain-fall gating.

## What T-14/T-20/T-21 need to know
- The NoWebGL SVG's screen-space projection is a plain isotropic scale (not a perspective match to
  the real camera) — it's a legible, composed kolam, not a pixel-accurate re-projection. Acceptable
  per DESIGN §8b's own framing ("a composed frame, not a debug dump"), but don't read it as
  geometrically identical to the WebGL render for the same seed/path (pc-red-team's T-21 attack #5
  says "confirm its geometry agrees with the WebGL render" — it agrees in the sense of using the
  same core `emit()` output and the same D4 symmetry; it does **not** agree pixel-for-pixel because
  of the different projection. Worth stating precisely in whatever writeup references this.)
- `SceneErrorBoundary`'s catch path and the `webglcontextlost` path are both real code but neither
  was exercised by a live browser test — see above.
