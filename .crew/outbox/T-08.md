# T-08 outbox — The grain renderer

## What I built
`src/render/Grains.jsx`, `src/render/grain.vert.js`, `src/render/grain.frag.js`, plus three small
shared modules the shader/renderer need: `src/render/lightRig.js` (DESIGN §6.4 constants),
`src/render/palette.js` (DESIGN §1.1 hex tokens), `src/render/grainConstants.js` (DESIGN §6.7),
`src/render/glslNumber.js` (formats a JS number as a GLSL float literal, used to splice sim.js's
constants into the shader string).

- `Grains.jsx`: one `THREE.BufferGeometry` built once (`useMemo`), capacity 20000, attributes
  `position`/`aBirth`/`aPhase` (`DynamicDrawUsage`), `setDrawRange(0, 0)` until the first write. A
  `forwardRef` component exposing `pushRange(offset, n, sourceBuffer)` via `useImperativeHandle`.
  `useFrame` does exactly two uniform writes (`uTime`, `uScale`) — no `new`, no array method, no
  `setState`.
- `grain.vert.js`: `positionAt`'s algebra reproduced in GLSL, with `SPAWN_HEIGHT`/`FALL_TIME`/
  `BOUNCE_TIME`/`BOUNCE_DAMPING` imported live from `core/index.js` and spliced in as literals (if
  sim.js's constants ever change, this file's build output changes with them — no hand-copying).
  Also computes `vKeyDirView`/`vKeyFalloff`/`vFlight`/`vTint` for the fragment shader and the
  perspective-correct, clamped `gl_PointSize`.
- `grain.frag.js`: DESIGN §6.5's shader copied structurally verbatim — the fake-hemisphere-normal
  trick from `gl_PointCoord`, the warm-key/cool-rim split, the 3-stop tint ramp, the soft edge.

## Golden-vector fence — verified by hand, not just claimed
I hand-evaluated the shader's algebra against all 12 vectors in
`tests/sim.test.js::test_sim_matches_shader_reference_vectors`. **11 of 12 match exactly** (modulo
float32 rounding, which is below visual/positional significance at this scale). **The 12th does
not, and cannot, on real GPU hardware:**

- Golden vector 11 is `args [-3.5,0,4.25,2,0.5,2.6] -> y = 7.460698725481049e-16`.
- I traced this by hand: in **float64** (JS), `2.6 - 2 = 0.6000000000000001`, which is *not* `<
  FALL_TIME (0.6)`, so `positionAt` takes the **bounce branch** — `bounceLocal =
  1.1102230246251565e-16`, and the tiny resulting `y` is exactly the golden value.
- In **float32** (verified with `Math.fround`), `2.6f - 2.0f = 0.5999999046325684`, which *is* `<
  FALL_TIME32 (0.6000000238418579)` — the **fall branch** is taken instead, giving a different
  tiny value (~3.8e-14 by direct calculation), not `7.46e-16`.
- Both values are visually and numerically "settled" (the grain is at rest either way) — this is a
  **hardware float32-vs-float64 precision limit landing exactly at a `t - birth == FALL_TIME`
  boundary**, not an algebra mismatch. It cannot be closed by writing the shader differently; the
  only fix would be evaluating position in float64 on the GPU, which WebGL doesn't offer. Documented
  in `grain.vert.js`'s header comment rather than hidden. **Flagging as a needs-decision** in case
  pc-red-team or pc-scribe wants this named explicitly as a known limit (I don't think it needs a
  fix — the visual claim "the grain is at rest" holds either way — but it's not my call to close
  silently).

## Deviations from DESIGN.md — flagged, not silently worked around
1. **No `aTint`/`aSize` buffer attributes.** DESIGN §6.7 puts a requirement on pc-backend (T-06) to
   generate these inside `core/grains.js` and store them in the `GrainBuffer`. They didn't land —
   T-06's outbox lists the `GrainBuffer`'s public fields as exactly `origin, birth, phase, count,
   cursor, print, capacity`, no `tint`/`size`. Since I cannot modify the frozen core, I derive a
   per-grain tint ramp position and size-jitter factor **in the vertex shader** from `aPhase`
   (already seeded, already in the buffer, already part of what determines `birth`'s ordering)
   via a cheap deterministic GLSL hash (`hash11`) — not `Math.random()`, and fully reproducible
   under replay (same seed + path -> same `aPhase` values -> same derived tint/size). This is
   **not** literally "part of the print" (the FNV hash only covers `origin`), so a hypothetical
   attack that changed only `phase` while leaving `origin` untouched could, in principle, change
   the visual appearance without moving the print — pc-red-team should know this if attacking the
   determinism claim at that level of precision. **needs-decision** for pc-architect: either amend
   T-06 to add real `aTint`/`aSize` arrays (small, could land later without touching this file's
   API), or accept the phase-derived approach as the shipped behaviour.
2. **`GRAINS_PER_SAMPLE = 4` from DESIGN §6.7 is not implemented.** `core/grains.js`'s `emit()`
   jitters and orbits **exactly one point per resampled arc-length sample** (-> 8 grains per
   sample via D4), not four scattered points per sample (-> 32). DESIGN's radial/centre-biased
   scatter (`r = SCATTER * rng()`) also isn't what `emit()` does — it does per-axis square jitter.
   Both are core-level behaviours I cannot change. The visible result is correspondingly ~4×
   sparser than DESIGN's density description, though the mechanism, symmetry, and determinism are
   all correct. Flagged for the same reason as above — not a silent substitution.
3. **§6.6's ground shader (wet stone, GLSL noise, fresnel sheen) is *not* built here** — DESIGN
   §10's own board-mapping table assigns it to T-11, and BOARD's T-08 acceptance criteria don't
   ask for it. `Ground.jsx` is otherwise untouched from the T-02 stub except the flat colour, which
   I changed from an arbitrary `#141414` to `--stone-800 (#0B0F12)` so the frame reads coherently
   until T-11 lands the real material.

## What I pulled forward from T-11's nominal scope, and why
DESIGN §10 assigns §6.1 (renderer color management/tone mapping), §6.2 (camera), and §7.3 (bloom
post settings) across T-02/T-11 rather than T-08, but none of those numbers are provisional in
DESIGN — they're fully specified constants, not decisions T-11 still has to make. Emissive grain
values only read correctly with `ACESFilmicToneMapping` + `Bloom` in place (§6.5's own comment: the
two are "a pair," retuned together), and the Crew Chief's task explicitly asked for a working
"signature frame" screenshot. So `Scene.jsx` now carries:
- The real camera: fov 32, base position `(-0.22, 2.35, 2.95)`, `lookAt (0, 0.02, -0.10)`, the
  responsive dolly formula, **pitch 38.5°** (per this task's explicit instruction, superseding
  PLAN.md's "~35°").
- `gl.toneMapping = ACESFilmicToneMapping`, `toneMappingExposure = 1.05`, `outputColorSpace =
  SRGBColorSpace`.
- A minimal `EffectComposer`: `Bloom` (intensity 1.15, luminanceThreshold 0.28, luminanceSmoothing
  0.22, mipmapBlur, radius 0.72, levels 6) and `Vignette` (offset 0.28, darkness 0.72), both at
  DESIGN §7.3's exact settings. **Not** included: `DepthOfField` (explicitly off-by-default, T-17)
  and film-grain `Noise` (reduced-motion-gated, more naturally T-11/T-13's call).

T-11 should feel free to retune any of the above — nothing here is meant to be load-bearing for
T-11's own acceptance criteria (every DESIGN numeric value still needs verifying against the diff
per its own acceptance #1), it's just already wired so the signature moment reads correctly now
instead of clipping to flat white.

## What T-09/T-11/T-14 need to know
- `pushRange(offset, n, sourceBuffer)` copies `sourceBuffer.origin/birth/phase` into the geometry's
  own typed arrays via `.set()` — **the two are separate memory**, `createBuffer()` allocates its
  own arrays internally and there's no way to share the underlying buffer without modifying core.
  Ring-wrap splitting (calling `pushRange` twice when one `emit()` call's writes cross the array
  boundary) is the caller's job — `Grains.jsx` only ever touches one contiguous range per call.
- `uEmissiveGain` is wired but held at `1.0` — the settle-breath (`1.00 -> 1.32 -> 1.00` over 1.2s,
  DESIGN §3.2) is T-14's job.
- `vAlpha` is wired but held at `1.0` — the Walk-Over fade (ring-wrap recycling) and the Sweep
  radial fade aren't implemented; DESIGN §10 doesn't actually assign the Walk-Over state to any
  task explicitly, worth a decision on whose job it is.
