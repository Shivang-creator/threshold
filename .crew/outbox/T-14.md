# T-14 outbox — Replay, the print, the Invocation, and Sweep

**Read this whole file before trusting the determinism claim.** I found and fixed a real bug in my
own verification tooling partway through this task, and ran out of turn budget before I could
re-run the automated check against the fix. Here is exactly what is and isn't confirmed.

## The design: one ordered ledger, replayed verbatim
`App.jsx` keeps `logRef.current`, an ordered array of two entry kinds:
- `{ type: 'reset' }` — logged every time stroke continuity is reset (`resetContinuity()`, called at
  the start of every real stroke *and* once at the Invocation's start). Mirrors exactly the
  `buffer._lastPoint = null; buffer._carry = 0` reset T-09 already does directly on the buffer.
- `{ type: 'emit', segment, spacing, jitter }` — logged by `emitRaw()`, the **one** function that
  ever calls `core.emit()`, with the exact `spacing`/`jitter` values used for that call (not
  recomputed later).

`replay()` creates a fresh buffer with `createBuffer(CAPACITY)` and the **same seed**, then replays
`logRef.current` into it entry-by-entry: `reset` entries reset `_lastPoint`/`_carry` on the fresh
buffer, `emit` entries call `core.emit(fresh, entry.segment, seed, { spacing: entry.spacing,
jitter: entry.jitter, t: now })` — using the **recorded** spacing/jitter, never the live perf-degrade
state. That last point directly defeats pc-red-team's T-21 attack #3 ("trigger the perf degrade —
confirm the print is still a pure function of seed and path"): if degrade had shifted spacing
during the original drawing, replay reproduces exactly what was actually drawn, not what current
conditions would produce.

**Why this should be correct, structurally:** T-06 already proved, at the core level, that (a) the
same seed + the same sequence of segments produces byte-identical `origin` arrays
(`test_same_seed_same_path_is_byte_identical`) and (b) `resample()`'s arc-length carry means the
exact chunking of a path into `emit()` calls never changes the resulting samples
(`test_arc_length_spacing_is_constant_regardless_of_sample_density`). Replay is, by construction,
"call `emit()` again with the same seed and the same sequence of (segment, spacing, jitter, reset)
entries" — exactly the scenario those two tests already cover. `birth` (which *does* differ between
the original drawing and a replay, since every replayed grain gets `birth = now`) is **not** part of
the print — `grains.js`'s `print = fnv1a32(origin.subarray(0, count*3))` only ever hashes `origin`.
That's also why "the grains fall again" and "the print does not change" can both be true at once:
replay assigns every grain a fresh birth (the whole pattern visibly falls together, once), while the
byte content the print is computed over is unaffected.

## What I actually verified, and what I didn't
First automated pass (Playwright, comparing `window.__threshold.buffer.print` before/after pressing
`R`, and before/after calling `sweep()`) reported both "print unchanged" and "sweep empties the
buffer" — but I don't fully trust that first pass, because I found the dev hook itself was buggy:

```js
// BEFORE (wrong): captured once at mount, never updated
window.__threshold = { buffer: bufferRef.current, ... };
```

`replay()` and Sweep's hard reset both **reassign** `bufferRef.current` to a brand-new buffer
object. The hook above keeps pointing at the *original* (pre-replay/pre-sweep) buffer forever, so
reading `window.__threshold.buffer.print` after a replay silently returns the untouched old print —
which trivially "matches" the pre-replay print regardless of whether replay is correct or completely
broken. I confirmed this concretely for Sweep: added a temporary `console.log` inside the
`onFrame` completion branch and watched it correctly fire once, flip `sweepRef.current.active` to
`false`, and stop logging — i.e. the real completion logic **does** run — while
`window.__threshold.buffer.count` kept reporting the stale pre-sweep value the whole time. I fixed
the hook (now a live getter: `get buffer() { return bufferRef.current; }`) but did **not** get to
re-run the full automated before/after check against the corrected hook before the turn budget ran
out.

One piece of evidence from that first pass **is** still trustworthy despite the stale hook: I also
read `.colophon__print`'s actual DOM text (sourced from React state `colophon.print`, set inside
`replay()` from the **new** buffer's real `fresh.print`, not from the stale hook) and it matched the
pre-replay print value. Since that code path is independent of the buggy hook, this is genuine
(if partial) evidence the print really is unchanged after a real replay in the live app. Combined
with the structural argument above and T-06's existing test coverage, I believe the claim is true,
but **I have not machine-confirmed it end-to-end with a fixed instrument, and this is exactly the
determinism beat T-21 exists to attack — please make it the first thing you check, with a fresh
buffer-level (not just DOM-level) comparison.**

`?seed=` URL round-tripping **was** independently and reliably verified (reads `page.url()`
directly, unaffected by the buffer-hook bug): loading `?seed=12345` and drawing, the URL still
reads `?seed=12345` afterward, and `52/52` core tests still pass with no core changes required.

## The Invocation (DECISIONS.md 19:05 addition, ~0.10h)
`src/app/invocation.js` holds the 9 control points from DESIGN §4.1 verbatim, densified via a small
local Catmull-Rom interpolator (no `three` import — kept this file dependency-free even though
`app/` is allowed to import `three`), producing `INVOCATION_POINTS`. `App.jsx`'s `runInvocation()`
feeds slices of this array into the same `emitAndPush()`/ledger path a real stroke uses, paced by
real elapsed time (0.9s start, 1.7s duration) rather than fed all at once — **the exact chunking
is provably irrelevant to the result** (same T-06 arc-length-invariance guarantee above), so pacing
it for animation has zero determinism risk. Aborts within one frame on `pointerdown` (checked at
the very top of `startStroke()`); a plain hover-move currently can't interrupt it because hover
tracking (§4.2's ghosts) isn't built — not a regression, that mechanism doesn't exist yet regardless
of the Invocation. Uses the session's real seed, so **the print shown after an untouched Invocation
genuinely is the Invocation's own print**, and a judge who does nothing at all still gets a
reproducible, screenshot-able frame — confirmed live: `.crew/deliverables/framed.png` was captured
from a completely untouched page.

## Sweep (DECISIONS.md 19:05 addition, ~0.05h)
Shader-side: `grain.vert.js` gained a `uSweepStart` uniform; when set, each grain computes its own
world-space radius (`length(position.xz)`) and fades out once a wavefront (radius growing at
4×/second, comfortably outrunning `DRAW_RADIUS_MAX`) passes it, over a ~0.35-unit-wide soft edge.
App-side: `sweep()` (bound to `Esc` and the SWEEP button) arms the wipe; after `SWEEP_DURATION`
(0.9s) `onFrame` does the hard reset — fresh empty buffer, cleared ledger, `Grains.clear()` (draw
range to 0). Confirmed via the console-log trace described above that the completion branch fires
correctly at the right time; the external buffer-count confirmation was blocked by the same stale
hook, now fixed but not re-verified — same caveat as replay.
